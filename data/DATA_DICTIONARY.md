# Data Dictionary

Stand-in dataset for **TBX — BVP Tech Catalyst Hackathon**, "Build a Finance Assistant That
Actually Understands You".

It covers everything Section 4 of the problem statement promises: transactions, vendor payouts,
reconciliation status, chart of accounts, vendor list, and this dictionary.

---

## Provenance — what is real and what is not

| Layer | Source | Real? |
|---|---|---|
| Transactions, amounts, dates, vendors, chart of accounts, departments, funds, POs, contracts | [SF Vendor Payments (Vouchers)](https://data.sf.gov/d/n9pm-xkyq), City & County of San Francisco | **Real**, unmodified |
| Vendor payouts | Derived by grouping real transactions by vendor × payment date | **Real**, aggregated |
| `payment_status` (Paid / Pending / Retainage Held / Reversed) | Derived from the real `vouchers_paid` / `vouchers_pending` / `vouchers_pending_retainage` columns | **Real**, derived |
| `reconciliation.csv` — bank matching state, statement refs, variances, exception reasons | Generated | **Synthetic** |
| `vendors.payment_terms`, `vendor_payouts.payment_method` | Generated | **Synthetic** |

The SF source publishes paid/pending/retainage amounts but **not** bank-level reconciliation
state — no public dataset does, it is internal back-office data. That layer is therefore
generated by [02_normalize.py](../scripts/02_normalize.py).

The generator is **deterministic**: every synthetic value is seeded off a BLAKE2b hash of the
transaction id plus a fixed seed (`tbx-bvp-2026`), so re-running produces byte-identical output.
No `random` module, no timestamps, no run-to-run drift. Your evaluation set stays stable.

Source licence: public domain (City & County of San Francisco open data).

---

## Coverage

- **Window**: 2024-09-01 → 2026-08-31 (24 complete months)
- **Grain**: one row per voucher line item
- **Currency**: USD
- **Fiscal year**: SF's FY runs 1 July → 30 June, so FY2026 ≈ July 2025 → June 2026.
  But `fiscal_year` is the year the spend was **booked against** (the appropriation year),
  not something derived from `transaction_date` — see the warning under `transactions` below.
  Values run FY2018 → FY2027.

## Two builds

The column names and values below are identical in both; only the types differ.

| | SQLite (`data/finance.db`) | PostgreSQL (`tbx_finance`) |
|---|---|---|
| Money columns | `REAL` | `NUMERIC(18,2)` |
| Date columns | `TEXT` (`YYYY-MM-DD`) | `DATE` |
| Empty string in CSV | stays `''` | becomes `NULL` |
| Foreign keys | declared only | **enforced** |

That last row is why the Postgres build is the stronger check: it refused nothing on load, so
referential integrity is proven rather than asserted. The third row is the only one that
changes your SQL — `WHERE purchase_order <> ''` in SQLite is
`WHERE purchase_order IS NOT NULL` in Postgres.

Setup for either is in the [README](../README.md#postgresql).

## Tables

### `transactions.csv` — fact table

One row per voucher line. The main table the assistant queries.

| Column | Type | Description |
|---|---|---|
| `transaction_id` | TEXT | Primary key, `T0000001` |
| `voucher_id` | TEXT | Source voucher number; **may repeat** across lines of one voucher |
| `transaction_date` | DATE | `YYYY-MM-DD`, the payment date |
| `fiscal_year` | TEXT | Fiscal year the spend is **booked against**, `2018`–`2027`. Not derived from `transaction_date` — see warning below |
| `vendor_id` | TEXT | FK → `vendors.vendor_id` |
| `vendor_name` | TEXT | Denormalized for convenience |
| `account_code` | TEXT | FK → `chart_of_accounts.account_code` (sub-object level) |
| `account_name` | TEXT | e.g. `Pharmaceutical` |
| `category_name` | TEXT | Top COA level, e.g. `Materials & Supplies` |
| `department_code` | TEXT | FK → `departments.department_code` |
| `department_name` | TEXT | e.g. `DPH Public Health` |
| `fund_code` | TEXT | FK → `funds.fund_code` |
| `fund_name` | TEXT | e.g. `SFGH-Operating Fund` |
| `program_code` | TEXT | `OPR` operating, `CAP` capital, etc. |
| `program_name` | TEXT | Expanded program label |
| `purchase_order` | TEXT | PO number, may be blank |
| `contract_number` | TEXT | Contract id, may be blank |
| `contract_title` | TEXT | Free-text contract description |
| `amount_paid` | REAL | Amount actually disbursed. **Can be negative** (reversals/credits) |
| `amount_pending` | REAL | Approved but not yet disbursed |
| `amount_retainage` | REAL | Withheld under contract retainage terms |
| `amount_total` | REAL | `paid + pending + retainage` |
| `payment_status` | TEXT | `Paid` \| `Pending` \| `Retainage Held` \| `Reversed` |

> **Aggregation note.** For "how much did we spend", sum `amount_paid`. `amount_total`
> includes money not yet out the door. Getting this distinction right is exactly the kind of
> thing the grounding criterion rewards.

> **⚠ `fiscal_year` is not the same as the date window.** It records which fiscal year's
> budget the payment was charged to. 98.3% of rows align with the Jul–Jun window of their
> `transaction_date`, but **17,747 rows (1.7%) are back-dated** — money paid recently to
> settle obligations booked as far back as FY2018. So the two obvious readings of
> "spend in FY2026" disagree by **$1.34 billion**:
>
> | Interpretation | Transactions | Total paid |
> |---|---|---|
> | `WHERE fiscal_year = '2026'` | 511,237 | $16,823,239,767.06 |
> | `WHERE transaction_date` in Jul 2025 – Jun 2026 | 519,233 | $18,160,356,066.39 |
>
> Neither is wrong — they answer different questions ("what did FY2026's budget fund?" vs
> "what money left the building that year?"). This is the single richest disambiguation trap
> in the dataset, and a strong assistant states which one it used rather than picking silently.

### `reconciliation.csv` — SYNTHETIC

One row per transaction, 1:1 with `transactions`.

| Column | Type | Description |
|---|---|---|
| `reconciliation_id` | TEXT | Primary key, `R0000001` |
| `transaction_id` | TEXT | FK → `transactions.transaction_id` |
| `voucher_id` | TEXT | Denormalized |
| `vendor_id` | TEXT | FK → `vendors.vendor_id` |
| `transaction_date` | DATE | Denormalized |
| `ledger_amount` | REAL | Book amount = `transactions.amount_total` |
| `bank_amount` | REAL | Bank statement amount. Blank when no bank record exists |
| `variance` | REAL | `bank_amount - ledger_amount`. Blank when unmatched |
| `reconciliation_status` | TEXT | `Reconciled` \| `Unreconciled` \| `Partially Matched` \| `Disputed` |
| `bank_statement_ref` | TEXT | e.g. `BNK-202605-014732`. Blank when unmatched |
| `matched_date` | DATE | Date cleared. Blank unless `Reconciled` |
| `days_outstanding` | INTEGER | Days open as of 2026-08-31. `0` when reconciled |
| `exception_reason` | TEXT | Why it did not match. Blank when reconciled |

**Status meanings**

- `Reconciled` — ledger line matched a bank line exactly, zero variance.
- `Unreconciled` — no bank record found yet. Reasons: no matching bank record, timing
  difference in transit, not yet cleared, missing remittance advice.
- `Partially Matched` — a bank line was found but the amount differs. Reasons: amount
  mismatch, FX rounding, bank fee deducted, partial settlement. Variance is 0.1%–2% of the
  ledger amount, either direction.
- `Disputed` — flagged for manual review, no bank match. Reasons: vendor disputes amount,
  duplicate payment suspected, goods receipt not confirmed, contract under review.

**Model behind the synthesis.** Probability of being reconciled rises with age
(<15 days 55%, <45 days 82%, <90 days 93%, older 96.5%), and drops for payments ≥ $250k
(−4pp), ≥ $1M (−10pp), and negative amounts (−15pp). Unmatched items split
62% Unreconciled / 26% Partially Matched / 12% Disputed. So recent, large, and reversal
transactions cluster in the exception queue — which is how a real AP ledger behaves, and it
gives "which transactions are still unreconciled?" a non-trivial answer.

### `vendors.csv` — vendor master

| Column | Type | Description |
|---|---|---|
| `vendor_id` | TEXT | Primary key, `V00001`, assigned in alphabetical order |
| `vendor_name` | TEXT | As published by SF, unmodified — including casing and suffix variants |
| `is_nonprofit` | TEXT | `Y` / `N` |
| `primary_category` | TEXT | Most frequent COA category for this vendor |
| `payment_terms` | TEXT | **Synthetic.** Net 30 / 45 / 15 / 60 / Due on Receipt |
| `first_payment_date` | DATE | Earliest transaction in window |
| `last_payment_date` | DATE | Latest transaction in window |
| `transaction_count` | INTEGER | Rows in `transactions` |
| `total_amount` | REAL | Sum of `amount_total` |

> **Vendor name variants.** Of 7,905 names, 48 groups (96 names, ~1.2%) are the same entity
> under different surface forms — e.g. `NEW FLYER OF AMERICA INC` / `New Flyer of America
> Inc`, `D & D UPHOLSTERY INC` / `D&D Upholstery Inc`, `FOCUS CAMERA INC` / `Focus Camera
> LLC`. Not pervasive, but real: enough that `WHERE vendor_name = ?` will quietly undercount,
> and enough to justify fuzzy matching plus showing the user which vendors you matched.

## Joins

```
vendors           1 ──< transactions >── 1  chart_of_accounts
                          │  │  │
                          │  │  └────── 1  funds
                          │  └───────── 1  departments
                          └───────────  1  reconciliation   (1:1)

vendors           1 ──< vendor_payouts
```

- `transactions.vendor_id`      → `vendors.vendor_id`
- `transactions.account_code`   → `chart_of_accounts.account_code`
- `transactions.department_code`→ `departments.department_code`
- `transactions.fund_code`      → `funds.fund_code`
- `reconciliation.transaction_id` → `transactions.transaction_id` (1:1)
- `vendor_payouts.vendor_id`    → `vendors.vendor_id`

## Gotchas worth handling in the assistant

1. **`voucher_id` is not unique** — one voucher can have many line items. Count vouchers with
   `COUNT(DISTINCT voucher_id)`, not `COUNT(*)`.
2. **Negative amounts exist** — reversals and credit memos. `SUM()` handles them correctly;
   `SUM(ABS())` does not. Do not filter them out silently.
3. **`fiscal_year` ≠ a date range** — it's the budget year charged, not the payment date.
   The two readings of "FY2026" differ by $1.34B (see the warning above). "Last year" is
   ambiguous three ways: calendar 2025, FY2026 by column, or Jul 2025–Jun 2026 by date.
4. **`amount_paid` vs `amount_total`** — "spent" means paid; "committed" includes pending.
5. **Vendor name variants** — resolve fuzzily, but show the user which vendor(s) you matched.
6. **Data ends 2026-08-31** — questions about later periods must return "no data", not zero.
   Zero and unknown are different answers, and conflating them is exactly the failure mode
   the grounding criterion penalizes.
7. **Blank `bank_amount` / `variance`** — NULL in SQLite, not `0`. `AVG(variance)` silently
   skips them; be explicit about the denominator.
8. **Date filters must be ranges** — `substr(transaction_date,1,7) = '2026-08'` cannot use an
   index and scans all 1M rows (512 ms). Use
   `transaction_date >= '2026-08-01' AND transaction_date < '2026-09-01'` instead: 16 ms,
   identical result. `substr()` in `SELECT`/`GROUP BY` is fine.
